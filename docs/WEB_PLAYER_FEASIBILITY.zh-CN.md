# 浏览器看电视可行性——仅研究

[English](WEB_PLAYER_FEASIBILITY.md) | [简体中文](WEB_PLAYER_FEASIBILITY.zh-CN.md) · [进度](../PROGRESS.md)

## 需求与结论

导入验证后的 set1，提供频道列表、上一台、下一台和随机播放，大按钮适配手机和车内乘客浏览器，继续使用现有主机和端口。**本版本不开发、不部署播放器；现有页面仍是 QA 汇总。**

公网 HTTP/HLS 源在可达且有效的前提下可行。让 ECS 统一提供带鉴权的流，可以解决浏览器跨域并转换部分编码/封装，但不能修复上游不可达、过期、损坏或无法解密的源，也不能保证所有老旧车机支持输出格式。

建议按 **代理 → 重封装 → 必要时转码** 的顺序处理，不要每条频道都重新编码：

```mermaid
flowchart LR
    A[验证过的 set1] --> B[频道 ID 查找与鉴权]
    B --> C{编码是否兼容}
    C -->|兼容| D[同源代理或重封装]
    C -->|不兼容| E[按需 FFmpeg 转 H.264/AAC]
    D --> F[HLS 网关]
    E --> F
    F --> G[浏览器原生 HLS 或 hls.js]
```

只运行正在观看的频道，同频道可共享输出；无人观看后关闭进程，限制并发及缓存片段数量。播放优先于批量检测。当前四核部署没有已验证的 GPU 能力，不能假设存在 NVENC/VAAPI，也不能未经实测承诺多路实时 4K 转码。

## 核对过的候选项目

核对日期：2026-11-16。

| 项目 | 确认的范围 | 适用性和边界 |
| --- | --- | --- |
| [hls.js](https://github.com/video-dev/hls.js) | 借助 HTML video 和浏览器媒体能力播放 HLS | 适合简洁前端，不是服务端转码器，也不是万能解码器 |
| [IPTVnator](https://github.com/4gray/iptvnator) | 桌面、浏览器 IPTV 和自托管后端 | 可参考列表和换台，仍受浏览器编码能力限制 |
| [neTV](https://github.com/jvdillon/netv) | 服务端网关、直通/重封装、偏 GPU 的转码 | 完整系统候选，但须核对 GPU 依赖和 CPU 回退 |
| [CodingButter/webtv](https://github.com/CodingButter/webtv) | 跨平台 HLS、节目表、录制和代理功能 | README 不能证明用户方案里描述的“任意编码自动转码”能力 |

“WebTV”不是唯一项目名。落地前需要明确仓库、镜像、许可证和版本，不能仅凭名称就确认功能。

## 继续使用原 IP 和端口

可以保留公开入口，将流媒体网关与只读 QA 进程分开。以后由现有端口上的反向代理分别把 `/` 指向汇总、`/tv` 指向播放器、`/media/` 指向本机流媒体服务；不用替换已有 80/443 业务。HTTP 改 HTTPS 会改变访问协议，还需要终端信任证书；使用域名通常比直接假定 IP 证书可用更容易管理。

鉴权必须覆盖播放列表、分片及密钥/初始化请求，而不只是网页。后端只接受验证过的频道 ID，不接受任意代理 URL，避免成为开放代理。保留源所需 UA/Referer，不将私人地址送进第三方 CORS 代理。HLS 代理还须处理主列表、相对路径、独立音轨、字幕、密钥和初始化片段的地址改写。

运营商 UDP 组播需要在可访问该组播的网络里建立合适的上游转发；公网 ECS 不能代替加入别人的专网。本项目没有实现该转发。

## 交互和验证

- 上下换台循环遍历电视频道；随机播放排除广播，最好避免立刻重复。
- 提供明确的播放/重试、错误状态、全屏和横屏控件；带声音自动播放受浏览器用户手势策略限制。
- 以后可在失败时查询 Top3/Top5 做备用切换，而不只是停在错误画面。
- 用实际手机/车机验证换台耗时、起播、卡顿、音画同步、CPU 和峰值传输。
- 2～4 Mb/s 大约每人每小时 0.9～1.8 GB 媒体流量，不含额外开销；这不是云费用报价。

将来获准开发时，建议先限制为单路观看、720p/1080p H.264 + AAC、带鉴权的同源 HLS，以及 set1 换台/随机按钮，再根据 CPU 和延迟测试扩展。
