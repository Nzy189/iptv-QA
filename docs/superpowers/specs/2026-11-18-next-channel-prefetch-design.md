# 播放器"下一台预热"（服务端为主） · 设计文档（2026-11-18）

状态：设计已与用户确认（2026-11-18）：采用**服务端为主**方案，浏览器与 APTV 共用同一套服务端预热能力，前端只保留三档开关。待实施。

## 背景与动机

顺序换台时，用户点了 51 台，等它竞速出画；再切到 52，52 又要从头冷启动（DNS/TLS 握手、清单解析、首个分片下载），通常 1~3 秒。用户希望：**看 51 的时候，后端就把 52 也接入、筛好，切 51→52 接近秒开。**

用户后端是 **4C16G 的 ECS**，算力/内存充裕，可以把"脏活"放到服务端。这样一套能力同时服务两类客户端：

- **浏览器播放器**（`/tv/`，走 `/tv/play/<index>/<slot>`）。
- **APTV / Apple TV 等第三方 App**（走 token 竞速订阅 `/tv/playlist.m3u?token=...`，每频道 URL 指向 `/tv/race/...`）。

APTV 上"下一台预热"只能靠服务端实现（它不加载我们的前端）；服务端方案天然覆盖它。

关键事实（已核实）：

- 服务端已有**每频道并发竞速 + 胜者缓存**：`_race_winner()` / `race_cache`，TTL 约 60 秒（`service.py:389`）。预热可直接复用这套缓存，命中即省一次竞速。
- 浏览器会话保存了 `channels` 顺序与当前 index，服务端能算出"下一台"；token 订阅的 view 顺序来自 `library.view(view)`，同样可算下一台。
- 浏览器与 APTV 的媒体都经同源代理转发（`serve_url` / `fetch_upstream`）；把预取缓存接入中继即可让两类客户端都受益。
- 转码默认仅 2 并发槽、90 秒空闲回收；4 vCPU 上每个 ffmpeg 都很吃 CPU，**不预热转码台**。

## 能力边界（避免高估）

- **服务端能**：预连接源站、预拉清单与前几片分片、预跑竞速选线路、把结果缓存。切台时冷启动里最贵的握手+清单+首片被吃掉。
- **服务端不能**：替客户端解码/渲染。客户端仍有一小段"解析+解首帧"成本。**"0 延迟"做不到，"接近秒开"可以。**
- **真正瓶颈是公网出口带宽与源站限流，不是 CPU/内存**。预热会多开上游连接、多拉分片。故必须守住：只预热"下一台"、只取前 2~3 片、缓存有 TTL/LRU 上限、并发预热有上限。

## 用户确认的决策

1. **服务端为主**：新增 `Prefetcher` 组件，浏览器与 APTV 共用。
2. **只预热下一台**（顺序里的 `index+1`，越界回绕），不预热上一台。
3. **三档开关 `关 / 轻量 / 完整`**：浏览器控制栏按钮 + `localStorage('tv-prefetch')`，默认**轻量**；APTV 无开关，用服务端配置档位，默认**轻量**。
4. **转码台一律不预热**。
5. 浏览器端**不再做**"隐藏 video 元素预缓冲"（客户端能力，留作二期可选增强）。

## 设计

### 新增组件 `iptv_qa/playback/prefetch.py`

`Prefetcher`（每个服务实例一个）：

- **缓存**：有界 LRU，键为 `(view, channel_id)` 或 `(scope, channel_id)`，受以下上限约束：
  - 最多预热 `max_channels` 台（默认 16）；
  - 字节缓存总量上限 `max_bytes`（默认 128MB，仅完整档使用）；
  - 条目 TTL 与 `race_cache` 一致的约 60 秒，过期驱逐；
  - 并发预热线程上限（默认 4），避免一次涌入大量上游连接。
- **`warm(view, channel_id, mode)`**（异步执行，不阻塞请求线程）：
  - 从 `library.view(view)` 取该台线路。
  - **light**：调用现有 `race_func(lines)` 竞速，把胜者写入共享 `race_cache`（复用 `_race_winner` 的存储与 TTL）。
  - **full**：light 基础上，把胜者的清单与前 2~3 片分片按上游 URL 预取进字节缓存，供中继直接回。
  - 命中已存在且未过期的条目则跳过。
- **`invalidate(channel_id)`**：线路变更/移除时清理；`shutdown()`：服务停止时释放线程与缓存。

### 中继集成（让缓存真正生效）

- `serve_url` / 媒体中继在拉取上游前先查 `Prefetcher` 字节缓存，命中直接返回（保留原有 UA/Referer 与清单重写逻辑）。仅命中 `(上游 URL)` 完全一致的请求。
- 轻量档不写字节缓存，只让竞速命中 `race_cache`：token 竞速端点直接拿到胜者、跳过竞速；浏览器起播前用 `GET /api/tv/prefetch?index=` 取"胜者线路槽位提示"，从服务端已预热的胜者线路起播（不再从第一条线路顺序起播）；第二期再由清单/分片字节缓存为预热过的重放加速。

### 触发方式

- **浏览器**：当前台起播成功后，前端按档位调用 `POST /api/tv/prefetch`，请求体 `{mode: 'off'|'light'|'full', source_id}`；服务端从会话算出"下一台"并 `warm()`。`off` 时前端不发请求（并在本地作废已有预热提示）。
  - 前端仍保留三档按钮（`id="prefetch-btn"`，与 `race-btn` 并排），文案 `下一台预热：轻量`，`localStorage('tv-prefetch')` 记忆；随机模式不触发。
- **APTV**：`serve_token_race()` 命中某频道后，按服务端配置档位异步 `warm(view, next_channel_id, mode)`，供下一次切换命中。APTV 无需任何改动。
- 客户端切换/翻页很快时，服务端只维护"当前会话的下一台"，旧目标按 LRU/TTL 自然淘汰，不做复杂取消。

### 配置与开关

- 服务启动参数 / 环境变量（形如 `--prefetch-mode=off|light|full`、`--prefetch-max-channels`、`--prefetch-max-bytes`），默认 `light`、16 台、128MB。
- 浏览器按钮与 APTV 配置共用同一 `Prefetcher` 实例与缓存，互不冲突。

### 边界与失败回退

- 预热失败（源站超时/限流/线路失效）静默丢弃，不影响正在播放的台，也不弹错。
- 缓存/预取不得改变任何"选择哪条线路"的正确性：与实时 view 不一致（`410/404`）时按现有冷启动逻辑处理。
- 随机换台模式不预热（"下一台"不确定）。
- 关闭档时 `Prefetcher` 不创建任何预热任务，行为与现状完全一致。
- 容量守恒：字节缓存与 race 缓存都设硬上限并有驱逐，**不会因长跑把 16G 内存吃满**。

### 测试与验证

- 新增 `tests/`（Python）覆盖 `Prefetcher`：LRU 驱逐、TTL 过期、三档行为、并发上限、关闭档不动作、命中 `race_cache`、字节缓存命中与回退。
- `python -m unittest discover -s tests -v` 全量回归。
- `node tests/player_navigation.test.js`：三档按钮按档位调用 `/api/tv/prefetch`、`off` 不发请求、随机模式不发。
- **真实源实测**（唯一有效证据，不用夹具冒充）：
  - 浏览器：关 / 轻量 / 完整 下 51→52 起播耗时对比。
  - APTV 路径：连续两次调用 `/tv/race/...`（预热开/关）对比胜者返回耗时。
  - 记录单/多客户端并发下的出口带宽与源站是否限流。

## 分期建议

- **第一期**：`Prefetcher` 的**轻量档**（预竞速写 `race_cache`）+ 三档开关 + APTV 触发 + 浏览器胜者线路槽位提示 + 配置项。浏览器起播时先查询已预热的胜者线路槽位、从该线路起播，因此浏览器与 APTV 都真正受益；第二期再加入清单/分片字节缓存进一步加速。
- **第二期**：**完整档**（清单+首片字节缓存接入中继）。收益更大但需改媒体中继路径，单列验证。

**已确认：分两期落地。**

## 非目标（YAGNI）

- 不预热上一台、不预热随机目标、不预热转码台。
- 不做客户端隐藏 video 预缓冲（二期可选）。
- 不预热整个频道列表，只预热当前会话的下一台。
- 不改检测、发布、总表数据与 OBS 行为。

## 已确认决策

- **分两期落地**（一期轻量档；二期完整档字节缓存）。
- 完整档**预取前 2 片**、字节缓存内存上限默认 **128MB**。
